# Observability

How the Api and Worker hosts log, correlate, trace, measure and report health. Decisions come from [ADR-007](../adr/ADR-007-observability-and-configuration.md) (correlation header name from [ADR-006](../adr/ADR-006-api-conventions.md)); this page describes the implementation (T-008b).

## Logs
- **Format:** the built-in `Microsoft.Extensions.Logging` JSON console formatter (`Logging:Console` in each host's `appsettings.json`): one JSON object per entry with `State` (structured values), `Scopes` (`IncludeScopes`) and a UTC timestamp. Every scope carries `TraceId`, `SpanId` and `ParentId` (activity tracking, set in code), so a problem's `traceId` (`00-<TraceId>-<SpanId>-01`) can be found in the logs. Write log statements with `[LoggerMessage]` and explicit values only.
- **Log policy, enforced in code** (`Observability/LogPolicy.cs`, one copy per host, identical except the namespace). It wraps the host's `ILoggerFactory`, so no configuration source can loosen it:
  1. An entry at **Warning or above never carries an exception object or text built from one**, whatever its category (EF Core, Npgsql, Kestrel, health checks, hosting, our code). The original entry moves to **Debug**; the Warning+ entry is replaced by a fixed one: `<EventName> failed with <ExceptionType>; message and exception are logged at Debug only`.
  2. **Floors:** the Api never enables `Microsoft.AspNetCore*` below Warning. Its Information and Debug entries print URLs with query strings and bound parameter values. The Api writes its own request log instead (`RequestLogMiddleware`): method, **route template** (never the path or the query string), status, duration. Seeing ASP.NET Core Debug logs needs a code change.
  3. **Debug-only categories:** the Api writes `Microsoft.Extensions.Diagnostics.HealthChecks` at Debug at most, because the health check service logs an Error for every failing probe; module checks log state changes themselves.
- **Never logged:** passwords, tokens, request or message bodies, query strings, exception messages at Warning+. `EnableSensitiveDataLogging` and `EnableDetailedErrors` stay off (tested for every `DbContext` in both hosts). Npgsql redacts PostgreSQL `DETAIL` text unless the connection string sets `Include Error Detail`; the policy keeps it out of Warning+ entries either way.
- **Seeing details:** set `Logging:LogLevel:<category>` to `Debug` locally (user secrets or an untracked settings file). Debug entries can contain exception messages and database error text: never enable Debug in shared environments.
- **Known limits:** the policy recognises exceptions by the exception object. A third-party entry that embeds an exception message in its text without passing the exception would not be caught (none was seen). EF Core's `ConnectionError` entry (Error, no exception) names the database and `host:port`.

## Correlation ID
- Header `X-Correlation-ID`. An incoming value is kept only if the request has **exactly one** value of **1–64 characters** from `[A-Za-z0-9._-]`; otherwise a new UUID v7 (`"N"` format, 32 hex digits) is generated. A rejected value is never logged. The ID is not a secret and is never used for authorization.
- `CorrelationIdMiddleware` runs first. It sets the request's `CorrelationContext`, opens a log scope `CorrelationId` for every entry of the request, and adds the response header in `Response.OnStarting` (the exception handler clears headers before a 500), so every status carries it. The problem-details body has no correlation member: use the header.
- **In process:** `ICorrelationContext` (SharedKernel, interface only) is an event-propagation abstraction. Hosts implement it per DI scope: the Api per request, the Worker per handled outbox message (`IntegrationEventContext`). Modules only read it; their dependency is optional (`ICorrelationContext? correlationContext = null`), so compositions without a host implementation write null.
- **Across hosts:** a module's outbox writes the value into `CorrelationId`. The Worker restores it for each handler: in the dispatcher's log scope and in the handler's `ICorrelationContext`, so events the handler publishes carry it. Without an ambient value it stays null.
- **Limits:** work started in a new DI scope inside a request does not see the value; server log entries written before the middleware runs (connection level) cannot carry it.

## Traces and metrics
- **OpenTelemetry** (no vendor SDK; backend not chosen). `Observability/TelemetrySetup.cs`, one copy per host. `Telemetry:Exporter` selects `Console` (default when unset) or `None` (collected for in-process listeners, nothing exported); any other value stops the host at startup. It is read from the final configuration when the providers are built. Logs are not routed through OpenTelemetry.
- **Api:** ASP.NET Core instrumentation (`OpenTelemetry.Instrumentation.AspNetCore`). `url.query` is removed from request spans, exceptions are not recorded as span events, and `/health/*` requests are not traced (they still count in the request metrics). Meters: ASP.NET Core, `TalepPazari.Api`, `Npgsql`.
- **Worker:** source and meter `TalepPazari.Outbox` (activity `outbox.dispatch`, kind Consumer, parent = the message's `TraceParent`, so one trace covers request → outbox → handler; counters `outbox.messages.dispatched`, `.failed`, `.dead_lettered`, tag `module`); meter `Npgsql`.
- **Not included:** Npgsql spans (`Npgsql` activity source; command text in spans was not reviewed for this task), outgoing HTTP instrumentation (no outgoing calls yet), OTLP (no backend).
- **`TalepPazari.Api` meter** (created through `IMeterFactory`; tag `http.route` = route template only):
  - `api.requests.client_aborted`: the client cancelled the request. The framework's exception handler ends it with 499 and never calls `ApiExceptionHandler`; the host logs one Debug entry and does not mark the span as an error. A cancellation the client did not cause stays a 500 with one Error entry (type only).
  - `api.responses.failed_after_start`: an exception after the response started. The request is aborted (see the API conventions), the request activity gets status `Error` and `error.type` = the exception type (no description, no exception event), and the framework's request-duration metric gets the same `error.type` tag.

## Health
- `GET /health/live`: the process only, no dependency; `200 Healthy`.
- `GET /health/ready`: every module's registered check; `200 Healthy` or `503 Unhealthy`. Plain text with the status only: the documented exception to the problem-details rule ([API conventions](api-conventions.md)), because orchestrators expect it.
- **Module checks:** a module registers a `HealthCheckRegistration` singleton in `Add<Name>Module` (package `Microsoft.Extensions.Diagnostics.HealthChecks.Abstractions` only); the Api adds every registration to its health check service. Register only the host's own critical dependencies (ADR-007), with a 3 s timeout. A check never throws: it resolves its dependencies inside `try`, returns Unhealthy with a fixed description and no exception object, logs the exception at Debug, and logs only state changes (one Warning when the dependency becomes unreachable, one Information when it is back), so repeated probes do not flood the logs. The Worker also runs `Add<Name>Module`; its registrations are unused.
- **Worker health (not implemented; ADR-007 Open, decided with the deployment target):** (a) a small HTTP listener with liveness from the dispatcher loop's heartbeat age and readiness from the module checks (standard probes; adds a port; recommended once an orchestrator is chosen); (b) a heartbeat record in the database (no port; needs a table, a watcher and cleanup); (c) an orchestrator-level exec or file check (cheapest; platform-specific).

## Decisions recorded with T-008b
- `ICorrelationContext` lives in SharedKernel as an interface only and is read as an event-propagation abstraction under ADR-002/ADR-007.
- The log policy and the telemetry setup are one small file per host (duplicated on purpose, no shared host project); revisit when a third host appears.
- No correlation member in problem details; logging library is the built-in `Microsoft.Extensions.Logging` (no Serilog/NLog).
